# 최종 2.0 이미지로 독립적인 바인드 마운트 재현

## 목적

과거 이미지 workshop-web:1.0 또는 기존 web-live에 의존하지 않고, 최종 소스에서 2.0을 새로 빌드해 검증한다. 과거 성공 기록은 유지하고 이번 재현 검증과 구분한다.

## 실행 구성

- 베이스·소스: 현재 web/Dockerfile 및 HTML·설정 템플릿.
- 컨테이너: 실행마다 workshop-bind-v2-시간-PID 형태의 새 이름.
- 환경 변수: NGINX_PORT=8080.
- 포트: 호스트 127.0.0.1:8083 → 컨테이너 8080. BIND_HOST_PORT로 호스트 포트만 바꿀 수 있다.
- 마운트: 이번 실행에서 mktemp로 만든 새 호스트 폴더 → /usr/share/nginx/html. 컨테이너에서는 읽기 전용이며 호스트는 파일을 수정할 수 있다.
- HTTP 검증: /bind-check.txt의 응답을 변경 전후 비교. 두 요청 사이 재빌드·재시작 없이 같은 파일만 변경한다.
- 정리: 이번 스크립트가 만든 컨테이너와 임시 파일·디렉터리만 제거한다. 기존 web-live·Compose 컨테이너·사용자 HTML은 수정하지 않는다.

## 실행 방법

Ubuntu/WSL에서 저장소 루트를 기준으로:

```bash
bash scripts/verify-bind-v2.sh
```

명령 추적과 실제 결과는 evidence/ch07/bind-v2-runtime.log에 기록된다. 같은 파일 이름의 검증 로그가 있으면 새 실행 결과로 교체한다. 기존 로그를 보존하려면 실행 전에 별도 보관한다. curl 실패 또는 응답 내용 불일치·정리 실패 시 PASS로 표시하지 않는다.

## 현재 검증 상태

**최종 결과: PASS.** [실제 실행 로그](bind-v2-runtime.log)를 도우미가 직접 읽어 확인했다. 아래 최초 실패·접근 제한 기록은 이전 시점의 상태다.

- 새 이미지 빌드: workshop-web:2.0.
- 새 컨테이너: workshop-bind-v2-1794313391-18190, ID ba1582b0a3f12013b2f1f58ac1a360f5815aacefc01d95a09f155995f8b0bef6.
- 새 호스트 폴더: /tmp/workshop-bind-v2.xS3VpM. 변경 전 drwx------, chmod 후 drwxr-xr-x, 파일 -rw-r--r-- 확인.
- docker inspect: 127.0.0.1:8083 → 8080/tcp 및 해당 폴더의 읽기 전용 바인드 연결 확인.
- 생성 설정: listen 8080; 확인.
- 첫 응답: BEFORE_HTTP_BODY=bind-v2-before.
- 호스트 파일 변경 후 응답: AFTER_HTTP_BODY=bind-v2-after.
- 두 요청 사이 빌드·재시작 없음. HTTP_COMPARISON=PASS.
- 이번 컨테이너·임시 파일·폴더 정리 성공. VERIFICATION_RESULT=PASS.

원인 가설을 뒷받침하는 증거: 재실행에서 mktemp 폴더가 실제 700이었고, 접근 가능한 755/644로 지정한 뒤 동일 서버 구성에서 HTTP가 성공했다. 최초 실패 컨테이너의 NGINX 오류 로그는 보존되지 않았으므로 최초 내부 오류 문구를 만들어 기록하지 않는다.

첫 실제 실행은 이미지 빌드·새 컨테이너 생성·8083:8080 매핑·바인드 연결까지 성공했으나 첫 HTTP 요청이 403으로 실패했다. [실패 로그](bind-v2-failed-403.log)를 보존했다. 원인 가설은 mktemp가 만든 소유자 전용 디렉터리(일반적으로 700)에 NGINX 작업 프로세스가 진입할 수 없다는 것이다. 첫 실행에서는 권한 조회·NGINX 오류 로그가 없으므로 확정 진단과 구분한다. 스크립트를 수정해 변경 전 권한을 조회하고 임시 디렉터리를 755, 공개 검증 파일을 644로 지정한 뒤 재조회하도록 했다. 실패 시 NGINX 로그도 수집한다. 재실행 결과는 아직 대기 중이다.

도우미 실행 환경에서 docker info는 Docker 설정 파일 및 API 접근 권한 오류로 실패했다. 따라서 이 문서 작성 시점에는 새 컨테이너 검증을 실행 완료로 기록하지 않는다. README 절차와 자동 기록 스크립트를 준비했고, 학습자 Ubuntu에서 실행 후 실제 로그를 확인할 예정이다.
